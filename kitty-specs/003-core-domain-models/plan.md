# Implementation Plan: Core Domain Models

**Branch**: `003-core-domain-models` | **Date**: 2026-03-24 | **Spec**: [spec.md](spec.md)

---

## Summary

Define 27 pure Kotlin source files in `core/domain/src/commonMain/kotlin/` implementing all 15 domain entities and 3 common value types across 6 bounded contexts. Every type is a `data class`, `enum class`, or `@JvmInline value class` — zero business logic, zero framework imports. All entities use typed ID value classes (`@JvmInline value class OrderId(val value: String)`) to prevent cross-entity ID confusion at compile time. Monetary values use `Money(val cents: Long)` to guarantee exact arithmetic.

## Implementation Phases

### Phase 1 — Common Value Types (unblocks everything)

Deliver `Money`, `Timestamp`, and `Duration`. These are imported by every other file in the feature; nothing else can be written until they exist.

**Deliverables**:
- `common/Money.kt` — `@JvmInline value class Money(val cents: Long)` with `ZERO` constant and `+`, `−`, `×(Int)` operators
- `common/Timestamp.kt` — `@JvmInline value class Timestamp(val epochMillis: Long)`
- `common/Duration.kt` — `@JvmInline value class Duration(val millis: Long)`

**Test**: Construct `Money(1099) + Money(501)` → `Money(1600)`; assert `Money.ZERO.cents == 0L`.

---

### Phase 2 — Ordering Bounded Context (P1 — unblocks Order)

Deliver all ordering entities in dependency order: `Category` → `Modifier` → `ModifierGroup` → `MenuItem` → `Section` → `Table` → `OrderStatus` → `SelectedModifier` → `OrderItem` → `Order`.

**Deliverables**: 10 files in `ordering/`

**Key constraints**:
- `OrderItem.unitPrice` and `SelectedModifier.priceAdjustment` use `Money` (snapshot, not a reference to `MenuItem.basePrice`)
- `Order.customerId` is `CustomerId?` — forward reference to the customer domain; the ID type is declared in `customer/Customer.kt` (implement in Phase 4), but only the ID type is needed here, not the full `Customer` entity
- `Order.items` allows an empty list (order may be built incrementally)

**Test**: Construct a full `Order` with two `OrderItem`s, one with a modifier, assert all fields accessible.

---

### Phase 3 — Payment Bounded Context (P1 — depends on Phase 2 for `OrderId`)

Deliver `PaymentMethod`, `PaymentStatus`, `Payment`, `ReceiptLineItem`, `Receipt`.

**Deliverables**: 5 files in `payment/`

**Key constraints**:
- `Receipt` is an immutable value object (a `data class` with all vals); it is derived by the service layer, not fetched from storage
- `Receipt.taxAmount` is stored as a snapshot (computed externally, passed in); `Receipt` does not compute tax itself
- `Receipt.total` == `Receipt.subtotal + Receipt.taxAmount` is a convention, not enforced by the domain model

**Test**: Construct a `Receipt` with two `ReceiptLineItem`s and two `Payment`s; assert `payments.sumOf { it.amount.cents }` equals the `total.cents`.

---

### Phase 4 — Customer Bounded Context (P2 — depends on Phase 2 for `OrderId` in back-reference scenarios)

Deliver `Customer` with its `CustomerId`.

**Deliverables**: 1 file in `customer/`

**Key constraint**: `Customer.loyaltyPoints` is non-negative by convention; enforcement belongs to the service layer.

**Test**: Construct a `Customer` and assert all optional fields (`phone`, `email`) are nullable.

---

### Phase 5 — Inventory Bounded Context (P3 — independent)

Deliver `UnitOfMeasure`, `IngredientStock`, `StockAlert`.

**Deliverables**: 3 files in `inventory/`

**Test**: Construct `IngredientStock` with `quantity = 1.5` and `alertThreshold = 2.0`; assert `quantity < alertThreshold` is `true`.

---

### Phase 6 — Staff Bounded Context (P3 — independent)

Deliver `Role`, `Employee`, `Shift`.

**Deliverables**: 3 files in `staff/`

**Key constraint**: `Employee.pinHash` stores a hash string, not the raw PIN. The domain model makes no assumption about the hash algorithm — that is enforced at the service layer.

**Test**: Construct an `Employee` with `role = Role.MANAGER`; assert `role.name == "MANAGER"`. Construct a `Shift` with no clock-out; assert `clockOut == null`.

---

## Parallelisation

Phases 4, 5, and 6 have no inter-dependencies and can be implemented in parallel after Phase 1 (common types) is complete. Phase 2 must precede Phase 3.

```
Phase 1 (common) ──► Phase 2 (ordering) ──► Phase 3 (payment)
                 └──► Phase 4 (customer)    [parallel]
                 └──► Phase 5 (inventory)   [parallel]
                 └──► Phase 6 (staff)       [parallel]
```

## Testing Strategy

- **Framework**: Kotest assertions in `commonTest`
- **Approach**: Construct entities via primary constructors; assert field values and relationships
- **No mocks, no fakes** — there are no interfaces or services in this feature
- **Coverage target**: All 27 entity files have at least one construction test confirming every field is accessible and nullable fields accept `null`
- **Money arithmetic**: At least 10 price-combination tests verifying no rounding errors (SC-003)

Test files live in `core/domain/src/commonTest/kotlin/com/vibely/domain/` mirroring the source package structure.
